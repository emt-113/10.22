> 状态：修订稿（2026-10-19）。基于外部评审意见对 v1 的逐条回应。
> v1 文档：proposal-health-engine-and-coach-v1.md（保留作对照）。

## 0. 修订记录（必须先说的事实修正）

- **机型判定修正**：团队真机为 **Redmi K70 Pro**（23117RK66C/manet），官方规格 **5000 mAh / 120W**——v1 误写为 K70E（5500mAh/90W），内置机型表已同步修正（5500 → 5000）。
- **基准含义翻转**：系统报告的实测容量 5000mAh ≈ 标称 5000mAh → **系统认为该电池健康度接近 100%**，而非 v1 所述"老化到 91%"。我们首次快充样本估出 67.5%，实际偏差约 -33%，进一步坐实"快充电流脉冲积分低估"。
- 5000mAh 的性质：**系统报告值**（dumpsys batterystats Estimated battery capacity），非独立测量。它可作为对照参照系，但验收文档中如实标注，不以它"证明"算法准确。

## 一、评审意见采纳表

| # | 评审意见 | 处置 | 说明 |
|---|---|---|---|
| 1 | 核实机型/容量基准 | **已采纳并修正** | 见修订记录 |
| 2 | 健康度从"尽力算出百分比"改为"可信才更新" | **采纳** | 与现有"待估算/快速/正式"三态天然兼容，升级为三档置信标签（低/中/高置信），数据不足时明确显示"估算中" |
| 3 | 分级数据源（直接报告 > 计数器差分 > 电流积分） | **采纳，附平台现实** | 目标机 Android 16 已锁死 power_supply sysfs（实测 Permission denied，shell 域亦然），"设备直接报告满充容量"一级在该机型不可得；机型表承担**先验**角色，计数器差分为主证据、电流积分为辅 |
| 4 | 方案 A 重构：电流大小只用于识别充电模式，不单独定权重 | **采纳** | P70 一刀切降权会误伤真实高电流数据。改为：电流分布仅做**充电模式标记**（快充段/平稳段），权重由一致性检验（见 #5）联合决定 |
| 5 | 方案 B 升级为数据质量检测 | **采纳** | 检测四类异常：计数器冻结、异常跳变、反向变化、长时间无更新；并与电流、SOC、时间互验，输出**信号可靠性评分** |
| 6 | 方案 C 改质量加权 | **采纳** | 取消无条件 3 倍权重；权重 = f(电量跨度、计量连续性、温度稳定性) |
| 7 | 方案 D 按需评估 | **采纳** | 仅在依赖电流积分的设备上评估 5s 采样的收益/耗电比；传感器本身不可靠时加密采样无意义 |
| 8 | 跨度门槛提高（≥20% 正式，30–40% 高置信） | **部分采纳（双轨保留）** | 正式引擎 25% 门槛不变；快速粗估保留 8% 门槛但**降级为"低置信度参考"标签**。理由：一刀切 20% 会让数字推迟数天出现，与"即时反馈"产品诉求冲突；用置信标签让用户自行判断比隐藏更诚实（另有 45–140% 荒谬值熔断兜底） |
| 9 | 滚动加权中位数整合多次结果 | **已具备** | 现引擎即中位数 + MAD 稳健加权，保留 |
| 10 | 亮屏三指标拆分（实际亮屏 / 连续使用时段 / 真实休息次数） | **采纳** | 纠正 v1 "有效使用 = 亮屏 − 短暂分心"的口径混淆 |
| 11 | 事件状态机 + 原始事件保留 | **采纳，分两步** | 第一步：统计层合并（低风险快速见效）；第二步：会话状态机重构（含重复事件/进程重启/缺失处理）。耗时计算已统一使用 `SystemClock.elapsedRealtime()`（单调钟，工程现状符合要求） |
| 12 | UsageStatsManager 的 SCREEN_INTERACTIVE 事件辅助核对 | **采纳（辅助）** | 用于交叉校验自记会话，不作为主数据源 |
| 13 | 提醒优先级：预算 > 连续使用 > 充电温度 > 深夜（二阶段） | **采纳** | 深夜场景延后且改为用户自设睡前时段 + 中性文案（不用"夜猫警报"类评判性表述） |
| 14 | 提醒防打扰设计（独立开关/冷却/免打扰/延后/"对我没用"反馈/每日主动提醒上限 2 次） | **采纳** | 全部进规则引擎设计 |
| 15 | 不得从充电行为推导健康度因果 | **完全采纳** | 原"夜间充电 3 次 → 健康 -0.5%"表述越界。改为行为陈述 + 一般性建议（"本周 3 次夜间长时间满电""长期满电停留可能不利电池寿命""可考虑启用系统充电优化"） |
| 16 | 设备档案系统（自动识别 + 搜索选择 + 自定义新增，本地 JSON/SQLite） | **采纳** | 见第三节；v1 的单条机型表升级为可扩展档案库 |
| 17 | 型号 ≠ 容量 ≠ 充电功率 ≠ 传感器可靠性，四者分离 | **采纳** | 档案提供先验，运行时探测（计数器/电流可用性、冻结行为）决定数据可信度 |
| 18 | 验收标准拆分（模块化） | **采纳** | 见第五节验收矩阵 |
| 19 | 三阶段路线（可信度 → 核心提醒 → 反馈闭环，游戏化延后） | **采纳** | 与"要提醒不要换皮"的产品定位一致 |

**保留意见**：仅 #8（门槛一刀切）——以置信标签替代强制隐藏，其余全盘或基本采纳。

## 二、修订后健康算法架构

```
先验层    设备档案（机型 → 标称容量 5000mAh、快充功率 120W）
证据层    L1 电荷计数器差分（主）——持续更新、方向合理、与 SOC 一致才可用
          L2 电流积分（辅）——计数器不可用时段的替代
          L3 满充锚点（高质量样本）——100% 端点 + 低电流保持确认
质量层    一致性检验：计数器 vs 电流 vs SOC vs 时间
          四类异常：冻结 / 跳变 / 反向 / 久不更新 → 信号可靠性评分
          充电模式标记：快充段 / 平稳段（本机电流分布自学习，零硬编码）
整合层    每次有效充电独立估算 → 滚动加权中位数（权重 = f(跨度, 连续性, 温度稳定)）
展示层    三档置信：低（快速参考）/ 中（初步）/ 高（一致）
          数据不足 → "估算中"；荒谬值（45–140% 区间外）→ 熔断不显示
```

## 三、设备档案系统

- **数据**：`assets/device_profiles.json`（品牌、型号代码、别名、标称容量、标称快充功率）；首版收录参赛测试机型 + 常见小米/Redmi/POCO 型号，随 App 版本更新
- **识别流**：`Build.MODEL/MANUFACTURER/DEVICE` → 本地库精确匹配 → 别名匹配 → 失败则引导手动搜索或自定义新增（品牌 + 型号 + 标称容量 + 可选规格来源）
- **用户确认制**：识别结果展示为卡片（"Redmi K70 Pro · 标称 5000mAh"），用户可一键确认或修改——识别是辅助，确认权在用户
- **不变式**：无网络权限；档案随 APK 发布；运行时传感器探测（计数器可用性、冻结行为、电流可读性）独立于型号匹配

## 四、亮屏统计修订

三个独立指标（口径不再混用）：
1. **实际亮屏时长**：所有亮屏区间之和（每日统计用）
2. **连续使用时段**：短熄屏（<30s，可配 15/30/60）合并后的会话跨度（疲劳/沉迷提醒用）
3. **真实休息次数**：熄屏达到休息阈值的次数（休息行为分析）

实现两步走：先统计层合并（快），后会话状态机重构（保留原始事件、处理重复/重启/缺失）。

## 五、验收矩阵

| 模块 | 验收方法 |
|---|---|
| 电池健康 | 以系统报告值（5000mAh）为对照参照系；分快充/慢充/不同跨度/温度场景分别测试；多次结果稳定性；低置信样本不得直接更新正式估算 |
| 亮屏统计 | 自动化用例：熄屏 5s/29s/30s/60s、重复事件、进程重启；合并后实际亮屏总时长不变 |
| 智能提醒 | 提醒关闭率、忽略率、"对我没用"反馈率、目标达成率；每日主动提醒 ≤2 次 |
| 产品可信度 | 相关性不得表述为因果；置信标签如实展示 |

## 六、路线图（三阶段）

1. **数据可信度**：机型表修正（已完成）→ 信号可靠性评分 → 置信标签 UI → 亮屏三指标 + 统计层合并
2. **三个核心提醒**：每日预算 / 连续使用 / 充电温度异常（规则引擎 + 独立开关 + 冷却 + 本地效果统计）
3. **反馈闭环**：周报、目标达成、健康度趋势、提醒有效率 → 之后才评估游戏化载体（脉搏星球等暂缓）
