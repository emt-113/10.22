## 一、电池健康度：当前方法与已暴露的问题

### 1.1 原理（行业标准做法）

```
健康度 = 实测满充容量 / 设计容量 × 100%
实测容量 = 一次充电的电荷净增量 × (100 / 充电跨度%)
电荷净增量 = 电流传感器积分（或系统电荷计数器差分）
```

### 1.2 实测发现的问题（Redmi K70E，120W 快充）

- 首次快充样本：估算 3306mAh（60.1%），真实约 5000mAh（91%）——**偏差 -40%**
- 原因：快充是动态大电流脉冲，10 秒采样间隔漏积分；且 MIUI 快充时系统电荷计数器冻结不更新
- 满充尾段（电流变小变平稳）估算自动回升到 67.5%——**算法有自我修正倾向，但单个快充样本不可信**

### 1.3 优化方案（按优先级）

**方案 A：充电功率自适应降权（不写死任何瓦数）**
- 问题：快充阈值因机而异（18W~240W 都有），写死 ">20W 算快充" 不可行；有的设备电脑 USB 充电全程只有 5W
- 做法：**每台设备自建电流基线**。前几次充电统计本机充电电流的分布（P50/P70/P90），电流 > P70 的采样段标记"高功率段"，参与容量计算的权重降为 0.3；低于 P50 的平稳段全权重
- 效果：120W 机器自动识别自己的快充段，5W 慢充设备全程平稳全权重，**零配置、零硬编码**

**方案 B：电荷计数器冻结检测（借系统之力）**
- 观察：快充时 MIUI 的电荷计数器（fuel gauge 累计电荷）冻结不动——系统自己都不信那时的读数
- 做法：计数器差分为主证据（精度高）；检测到"计数器冻结但电流不为零"的时段，视为不可信段直接丢弃
- 与方案 A 互补：一个看电流大小，一个看系统读数可信度

**方案 C：满充锚点加权（已有机制，加强权重）**
- 充到 100% 并保持低电流 5 分钟 → 起点百分比与终点 100% 都精确已知（消除量化误差）
- 这类样本权重设为普通样本的 3 倍，是收敛主力

**方案 D：平稳段加密采样**
- 检测到低功率平稳充电时，采样间隔 10s → 5s，积分精度翻倍（成本：耗电略增，仅在充电时）

**验收标准**：多次充电中位数落在系统自估 5000mAh ±5%（4750~5250）内视为合格。
当前状态：UI 已区分"快速估算/正式估算"徽标，误导风险已控制。

## 二、亮屏统计：短熄屏合并（用户痛点）

**问题**：点一下熄屏又马上点亮（刷视频时很常见），被拆成两个会话 + 一次"假熄屏"，统计失真。

**方案：宽限窗口合并**
- 熄屏后 **30 秒内**（可配置）重新点亮：不结束当前亮屏会话，那段熄屏计为会话内"短暂分心"，不累计熄屏时长、不计次数
- ≥30 秒才算真实熄屏
- 实现位置：统计层合并（读会话表时把间隔 < 阈值的相邻亮屏会话合并），不改实时服务，风险最小
- 顺手加一个统计口径："有效使用 = 亮屏 − 短暂分心"，更真实

## 三、产品灵魂：从"计时器"到"手机使用教练"

核心思路：**不是算时间，而是在对的时机说对的话**。所有提醒基于已有三类数据（亮屏会话、应用使用时长、电池/充电状态），无需新权限。

### 3.1 场景感知提醒（规则引擎，纯 Kotlin 可单测）

| 场景 | 触发 | 提醒示例 |
|---|---|---|
| 深夜刷机 | 23:00 后连续亮屏 30 分钟 | "夜猫警报：睡眠比刷视频值钱" |
| 单应用沉迷 | 同一 app 连续 45 分钟 | "该 app 已陪伴你 45 分钟" |
| 边充边玩 | 插电 + 亮屏 + 温度上升 | "边充边玩伤电池" |
| 连续疲劳 | 亮屏超 2 小时不断 | 护眼休息提醒 |
| 亮屏预算 | 自定义每日预算，超 80% 预警 | "今日 4 小时预算已用 85%" |

每个开关独立可关（个性化）；文案可自定义（个性化）。

### 3.2 目标与成就（正向激励）

- 每日/每周亮屏预算 + 达标连击（streak）
- 周进步报告："本周比上周少玩 3.5 小时"

### 3.3 差异化卖点：行为 ↔ 电池健康关联

- "本周夜间整夜充电 3 次，电池健康 -0.5% → 建议充到 80% 拔线"
- 把"少玩手机"与"电池长寿"两条动机绑定——数字健康类应用中独有

### 3.4 游戏化载体（可选）

候选：脉搏星球（充电/自律行为给星球供能，健康度差 → 星球枯萎）。定位为**激励系统的可视化层**，不是核心。是否做、做什么形态待定。
